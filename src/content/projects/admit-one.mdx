## Why I built it

My case studies describe checkout work I can't show: the code belongs to the companies I
built it for. admit-one is the same kind of problem, solved from scratch in public, so
you can read every line, run it, and try to break it.

It's an event-ticketing checkout. Pick tickets, they're held for you while you check
out, you pay, and you get your tickets. The interesting part is everything that can go
wrong in between — and a **chaos panel** that makes those things go wrong on purpose.

## The hard parts

**Holds that can't oversell.** Choosing tickets creates a hold with an expiry time.
Availability counts only _live_ holds, so an expired hold simply stops counting. There's
no background job to release it — which means no window where a dead hold still blocks
the next buyer.

**A step registry driven by the URL.** Each checkout step declares when it applies and
when it's complete; the flow is whatever applies to your order. The URL is the source of
truth, so refreshing resumes in place and a deep link can't skip ahead. It's a smaller,
open version of [the architecture behind my four-rail checkout](/work/four-rails-one-checkout/).

**The webhook decides, not the redirect.** Paying never returns "paid". The browser goes
to the order page, which waits for the payment provider's webhook. Payments carry an
idempotency key, so a retried request can't charge twice, and duplicate webhooks are
recognised and ignored. I wrote up the reasoning in
[The redirect races the webhook](/notes/redirect-races-the-webhook/).

**Payment after the hold expired.** If the money arrives after the tickets have gone,
the order is refunded in full and the page explains why — rather than overselling or
keeping the money.

## A seat map you can use with a keyboard

One concert has reserved seating: a 998-seat hall, drawn from static data and
server-rendered. Each section is a WAI-ARIA grid with a single tab stop. The arrow keys
step over aisles and move up to the seat _in front_, and every seat says its row,
number, tier, price and whether it's taken. Choosing seats is all-or-nothing: if one
has gone, nothing is held and the server names it. "Best available" lets the server
choose and hold in one step, keeping a party together without stranding a single seat.

## A waiting room for a flash sale

When 40,000 people (simulated) arrive at once, everyone queues first. Your place is
computed from when you joined and the clock, so a refresh keeps it. The page shows the
people ahead, a bar that only moves forward and a coarse wait. When it's your turn, it
says so and moves focus, but doesn't redirect you. Reserving is also rate-limited, with
a `429` and `Retry-After` that the page waits out exactly.

## Thirteen ways to break it

The chaos panel has thirteen scenarios:

- a declined card;
- 3-D Secure;
- a slow network;
- a connection that loses the payment's answer after the charge;
- a webhook that arrives twice, one that beats the browser, and one twelve seconds
  late;
- a hold that expires mid-payment;
- a crowd that buys the last ticket a moment before you;
- someone taking one of your chosen seats first;
- too many reservation attempts;
- a flash sale with a waiting room.

Each one is also an end-to-end test that checks both what you see and what the server
recorded.

## How it runs with no backend

The API is real HTTP — `fetch`, status codes, headers — served by a service worker in
your browser. That means there's nothing to deploy or configure, every visitor gets
their own sandbox, and the chaos panel can genuinely control the server. Because the
server lives in the page, its state is saved as it changes, including webhooks still
waiting to be delivered, so reloading mid-payment resumes exactly where you were.

The honest limit: one browser tab can't exercise true multi-client concurrency. The
README says exactly what a real database would do instead, and swapping one in means
deleting the `backend/` folder and the one line that starts it — a lint rule
guarantees nothing else depends on it.

## How it's built

The code is layered the way a larger team would need it: a shared kernel, a typed
HTTP contract, the simulated backend behind that contract, then features and routes.
Who may import whom is written down as a lint rule, so the architecture can't quietly
erode. Errors are [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details
with a typed code; every response is validated against the contract at the client;
and each screen's state is a single union, derived by a pure function, rather than a
pile of booleans. A refresh that fails keeps the last good data on screen instead of
replacing it with an error. Every response carries a Content Security Policy. The
repository documents all of it — architecture, conventions, API and eleven decision
records.
