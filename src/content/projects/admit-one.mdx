## Why I built it

My case studies describe checkout work I can't show: the code belongs to the companies I
built it for. admit-one is the same kind of problem, solved from scratch in public, so
you can read every line, run it, and try to break it.

It's an event-ticketing checkout. Pick tickets, they're held for you while you check
out, you pay, and you get your tickets. The interesting part is everything that can go
wrong in between — and a **chaos panel** that makes those things go wrong on purpose.

## The hard parts

**Holds that can't oversell.** Choosing tickets creates a hold with an expiry time.
Availability counts only _live_ holds, so an expired hold simply stops counting. There's
no background job to release it — which means no window where a dead hold still blocks
the next buyer.

**A step registry driven by the URL.** Each checkout step declares when it applies and
when it's complete; the flow is whatever applies to your order. The URL is the source of
truth, so refreshing resumes in place and a deep link can't skip ahead. It's a smaller,
open version of [the architecture behind my four-rail checkout](/work/four-rails-one-checkout/).

**The webhook decides, not the redirect.** Paying never returns "paid". The browser goes
to the order page, which waits for the payment provider's webhook. Payments carry an
idempotency key, so a retried request can't charge twice, and duplicate webhooks are
recognised and ignored. I wrote up the reasoning in
[The redirect races the webhook](/notes/redirect-races-the-webhook/).

**Payment after the hold expired.** If the money arrives after the tickets have gone,
the order is refunded in full and the page explains why — rather than overselling or
keeping the money.

## A seat map you can use with a keyboard

One concert has reserved seating: a 998-seat hall, drawn from static data and
server-rendered. Each section is a WAI-ARIA grid with a single tab stop. The arrow keys
step over aisles and move up to the seat _in front_, and every seat says its row,
number, tier, price and whether it's taken. Choosing seats is all-or-nothing: if one
has gone, nothing is held and the server names it. "Best available" lets the server
choose and hold in one step, keeping a party together without stranding a single seat.
[How the map works →](/notes/a-seat-map-a-screen-reader-can-use/)

## A waiting room for a flash sale

When 40,000 people (simulated) arrive at once, everyone queues first. Your place is
computed from when you joined and the clock, so a refresh keeps it. The page shows the
people ahead, a bar that only moves forward and a coarse wait. When it's your turn, it
says so and moves focus, but doesn't redirect you. Reserving is also rate-limited, with
a `429` and `Retry-After` that the page waits out exactly.
[Why the waiting room works this way →](/notes/a-waiting-room-should-tell-the-truth/)

## The price you see is the price you pay

Every price is all in from the first screen: the booking fee and GST included, with
what it's made of one line away. Adding fees at the end is drip pricing, which India's
dark patterns guidelines and the US FTC's fees rule both ban. One pricing engine serves
the server's charge and every label on screen. The GST rules are data: 18% on admission,
none at ₹500 or less, and 18% on the fee. Tax is worked out per ticket in paise, so a
ticket's price times the quantity is exactly the total.

## Card or UPI

Indian buyers can pay by UPI. Merchants can no longer send "collect" requests, so the
page shows a QR code on a computer, or a button that opens the UPI app on a phone. Both
carry the standard intent link, with the merchant category code and a reference unique
to the payment. The buyer approves in another app, so the page doesn't decide whether
they paid: it re-reads the order, and the webhook decides. A request runs out, never
outlasts the hold, and can be cancelled to pay by card. In the demo, a simulated phone
appears below the checkout so you can approve or decline.
[Why it's a webhook problem →](/notes/upi-is-a-webhook-problem-too/)

## The organisers' side

Organisers get a dashboard of their own. Sign in as one of three demo accounts, and see
only your organisation's events, and only what your role allows. The box office can read
and export but not refund, and the server refuses a refund even if the button were there.

- **Live sales:** tickets sold, revenue, sales by day, the funnel from reservation to
  ticket, and webhook lag. They update live over server-sent events, and you can pause
  them.
- **About 9,000 orders** in a table that stays fast and accessible. It draws about 30
  rows, but it's still a real table, so screen readers can tell where they are in the
  whole list. Filters live in the URL, and export goes to CSV.
- **Refunds** show as pending at once, and roll back if the payment provider refuses.
  [Why the table is still a table →](/notes/a-virtualised-table-should-still-be-a-table/)

## Every state, in a catalogue

Every screen and component has a story for each state it can be in, in a Storybook
catalogue, including states that are hard to reach by clicking: a failed load, a hold in
its last minute, a payment slow to confirm. The data comes from the same pricing rules
as the server, and a test checks it against the API's schemas. Components that fetch
their own data run on a fresh copy of the in-browser backend for every story.

- **Every story is a test:** it renders in a real browser, passes its own checks
  (keyboard models, focus, permissions), and has no accessibility violations.
- **Every story is a screenshot,** in light and dark, and at 375 px for whole screens.
  They're compared in Playwright's Linux image on ARM, both on my laptop and in CI,
  because screenshots only compare on the same kind of machine.
- **It found two bugs at once:** focus rings that `outline-none` should have removed,
  and busy buttons that could drop keyboard focus.
  [Why the machine matters →](/notes/a-screenshot-test-is-only-as-stable-as-its-machine/)

## The same API, on Postgres

Built in server mode, the app talks to a server instead of the browser sandbox: the
same API, answered by the same handlers, over Postgres. The same contract tests pass on
both, and so do the buyer's end-to-end flows.

- **No oversold tickets, no seat held twice:** the database refuses them itself, with one
  conditional update for tickets and a unique index for seats. Fifty buyers at the last
  ten tickets get exactly ten.
- **Payments and retries across processes:** a lock on the hold serialises everything
  about an order, and Idempotency-Keys are claimed in a table before any work starts.
- **Signed webhooks,** checked over the raw body and acted on once, in the same
  transaction as their effect.
  [Why the database is the lock →](/notes/the-database-is-the-lock/)

## Tickets that work in a basement

Doors are where networks fail, so neither the ticket nor the check needs one.

- **Signed tickets:** each ticket's QR code holds its details and an Ed25519 signature,
  so the door checks it with a public key alone, and refuses one that's been changed.
- **A wallet on the device:** tickets are kept in IndexedDB, and a service worker keeps
  the page, so they open in airplane mode.
- **A door scanner** that reads codes with the camera, or a photo, and remembers whom it
  has let in, so a ticket shown twice is caught. Only that page may use the camera.
- **Tested with a fake camera:** Chromium plays a video of a signed ticket, and the
  scanner reads it.
  [Why a signature, not a server →](/notes/an-offline-ticket-needs-a-signature-not-a-server/)

## Seventeen ways to break it

The chaos panel has seventeen scenarios:

- a declined card;
- 3-D Secure;
- a slow network;
- a connection that loses the payment's answer after the charge;
- a webhook that arrives twice, one that beats the browser, and one twelve seconds
  late;
- a hold that expires mid-payment;
- a crowd that buys the last ticket a moment before you;
- someone taking one of your chosen seats first;
- too many reservation attempts;
- a flash sale with a waiting room;
- a bank that declines a UPI payment the buyer approved;
- a UPI request that runs out before anyone approves it;
- a busy on-sale, with other buyers' sales landing live on the dashboard;
- a payment provider that refuses to start a refund.

Each one is also an end-to-end test that checks both what you see and what the server
recorded.

## How it runs with no backend

The API is real HTTP — `fetch`, status codes, headers — served by a service worker in
your browser. That means there's nothing to deploy or configure, every visitor gets
their own sandbox, and the chaos panel can genuinely control the server. Because the
server lives in the page, its state is saved as it changes, including webhooks still
waiting to be delivered, so reloading mid-payment resumes exactly where you were.

The honest limit: one browser tab can't exercise true multi-client concurrency. The
README says exactly what a real database would do instead, and swapping one in means
deleting the `backend/` folder and the one line that starts it — a lint rule
guarantees nothing else depends on it.

## How it's built

The code is layered the way a larger team would need it: a shared kernel, a typed
HTTP contract, the simulated backend behind that contract, then features and routes.
Who may import whom is written down as a lint rule, so the architecture can't quietly
erode. Errors are [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details
with a typed code; every response is validated against the contract at the client;
and each screen's state is a single union, derived by a pure function, rather than a
pile of booleans. A refresh that fails keeps the last good data on screen instead of
replacing it with an error. Every response carries a Content Security Policy. The
repository documents all of it — architecture, conventions, API and nineteen decision
records.
